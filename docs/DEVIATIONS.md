# Deviations from the submitted SRS, SAD and Test Plan

Mini-Project Part-2 asks for every deviation from the submitted documents to be recorded
and explained in the final demo. D1 to D7 were found in Sprint 1, D8 to D14 in Sprint 2.

| # | Document / section | What the document says | What we implemented | Why |
|---|---|---|---|---|
| D1 | SAD 3.6, 4.6 (technology) | Language, framework and database left open | Python 3.11+, Flask 3, SQLite, plain HTML/CSS/JavaScript | One small dependency, no build step, runs on every team member's laptop. The SAD left this as an implementation decision. |
| D2 | SAD Figure 2 (class diagram) | Identifiers (`userId`, `taskId`, ...) are Strings | Integer auto-increment keys | Native SQLite keys. Ownership is checked on the server, so predictable ids are not a security problem (TC-Sec-01). |
| D3 | SAD 4.3 (API design) | Four endpoints listed (login, create, update, delete task) | Those four as designed, plus about 30 more (full list in the README) | SAD 4.3 says paths "may be adjusted during implementation"; the extra endpoints are needed by the other requirements. |
| D4 | SAD Figure 2, `Status` enumeration | ACTIVE, COMPLETED, OVERDUE stored on the task | Only ACTIVE / COMPLETED are stored. OVERDUE is **derived** on every read (ACTIVE and due date in the past) and returned by the API; setting it by hand returns 400 (`app/status.py`) | A stored OVERDUE would be wrong the moment a due date passes, unless a background job kept rewriting rows. Deriving it keeps the list, the filters and the dashboard counts always correct (TMA-F-033). *Sprint 1 note: OVERDUE arrived with due dates in Sprint 2.* |
| D5 | Test Plan section 6 (tools) | Selenium, Postman, JMeter, Jira | pytest with Flask's test client for functional, security and performance tests; GitHub Issues and Projects for tracking; the UI also checked by hand in the browser | One toolchain that GitHub Actions runs on every pull request. TC-Perf-01 measures the p95 over 100 requests inside the test suite. |
| D6 | Test Plan section 7 (schedule) | Test execution 22-29 Sep 2026 | Tests run automatically on every push during both sprints (Oct 2026) | The course schedule placed implementation in October. |
| D7 | Sprint plan | Sprint 1: 19-23 Oct 2026 | Sprint 1 finished on 29 Oct (last PR, #38, merged that day) | Backlog and repository set-up took longer than planned. |
| D8 | Sprint plan | Sprint 2: 26-30 Oct 2026, 18 items in many small PRs | Sprint 2 ran 29-30 Oct as 8 larger PRs, each closing one member's related issues | Sprint 1 ran late (D7), so related issues were grouped to reduce review round-trips; every issue still has its own `Closes #N` and owner. |
| D9 | SAD 3.4 / Figure 1, Notification Service | External notification service "where enabled" | In-app notifications fully implemented; the e-mail channel is an interface-level stub (`EmailNotifier`), off by default | Test Plan section 4 tests third-party notification services only at the interface; SAD 4.6 lists choosing a provider as an open issue. |
| D10 | SAD Figure 2, `User` / `NotificationPreference` | Task preferences not modelled | `default_priority` and `default_sort` columns on `users` | TMA-F-041 says "notification **and task** preferences"; the class diagram had no place for task preferences. |
| D11 | SAD 3.9 (STRIDE, rate limiting "where appropriate") | No concrete rule | Login refused (HTTP 429) for 15 minutes after 5 failed attempts for one e-mail; every attempt logged | Brute-force protection noted in the STRIDE review; it is built on the TMA-SR-005 security log. |
| D12 | SRS TMA-SR-001 (HTTPS / TLS) | HTTPS between clients and backend | The app enforces HTTPS when `FORCE_HTTPS` is on (default in production): HTTP is redirected, HSTS is sent. TLS itself is provided by a reverse proxy in production and by a self-signed certificate locally (`python run.py --https`) | Certificates belong to the hosting environment, not the code. The demo runs on a laptop, where only a self-signed certificate is possible. |
| D13 | SRS TMA-NF-002 (99.5% monthly availability) | Measured availability | `/api/health` for uptime monitoring, documented production setup with automatic restarts and backups (`docs/DEPLOYMENT.md`); the monthly figure itself is not measured | Availability can only be measured on a deployed system over a month; the project runs locally. |
| D14 | SRS 2.2 (sync across sessions and devices) | "may support" | Data lives on the server, so any device that logs in sees the same tasks; no offline sync | SAD 4.6 left sync scope open; offline sync is out of scope for two sprints. |
